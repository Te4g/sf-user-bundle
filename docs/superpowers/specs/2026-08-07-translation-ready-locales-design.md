# Translation-Ready English and French Locale Design

**Date:** 2026-08-07

## Goal

Make the application generated by `te4g/starter` fully translatable in English
and French, and let visitors and authenticated users select their preferred
language from every generated page header.

The starter continues to generate application-owned code. It does not add a
runtime dependency on `te4g/starter`, change route URLs, or add JavaScript for
locale selection.

## Supported Locales and Fallback

The generated application supports `en` and `fr`. English is the default and
fallback locale. Locale labels are displayed as endonyms: `English` and
`Français`.

Generated locale configuration defines the supported locale map once so the
resolver, selector, validation, and templates do not maintain separate
allowlists. Application owners can extend that map and add matching catalogues
later.

## Locale Resolution

Each main request resolves its locale in this order:

1. the authenticated user's persisted `User.locale` preference;
2. the `app_locale` cookie;
3. the best supported language in the `Accept-Language` request header;
4. English.

A generated request subscriber runs after the Symfony security firewall has
restored the authenticated user. It validates every candidate against the
supported locale map, sets the request locale, and uses Symfony's
`LocaleSwitcher` so the translator and other locale-aware services use the
same value. Subrequests do not overwrite the resolved main-request locale.

The generated `User` entity gains a non-null locale column with an English
default, plus `getLocale()` and `setLocale()`. Registration initializes the
new user with the locale already resolved for that request, so browser or
cookie selection becomes the account's first persisted preference.

## Language Selection

A reusable Twig component is rendered in the public, authentication, and
authenticated headers. It uses an ordinary POST form with a select and submit
button, so the starter still generates exactly its existing two custom
Stimulus controllers.

The POST endpoint:

- requires a valid CSRF token;
- accepts only a configured supported locale;
- persists the locale through `UserRepository` when a user is authenticated;
- always writes an HTTP-only, SameSite=Lax `app_locale` cookie with a one-year
  lifetime;
- redirects to a submitted local absolute-path target only when it starts
  with one `/` and not `//`;
- otherwise redirects to the dashboard for authenticated users or the home
  page for visitors.

Unsupported locales return HTTP 422 and invalid CSRF tokens return HTTP 403,
without changing the user or cookie. No external or protocol-relative return
URL is accepted.

## Translation Coverage

All generated user-visible copy uses translation keys, including:

- document titles, navigation, headings, descriptions, buttons, empty states,
  dialog copy, and accessibility labels;
- form labels, help text, submission states, validation messages, and
  controller-added form errors;
- registration, authentication, account, locale-selector, and email copy;
- email subjects and HTML bodies.

Internal exception messages that are never rendered may remain fixed English
diagnostic strings.

The generated application contains complete, key-identical English and French
XLIFF catalogues. General UI and email copy use the `messages` domain.
Constraint and form validation messages use the `validators` domain where
Symfony expects it.

The application name remains application configuration rather than translated
copy. Translated titles interpolate that name as a parameter.

## Locale-Aware Email

`AccountMailer` receives Symfony's translator. Each public mail method selects
the recipient user's persisted locale, translates the subject explicitly in
that locale, and assigns the same locale to `TemplatedEmail` before rendering.
This keeps queued email subjects and bodies in the recipient's language even
when rendering happens outside the originating HTTP request.

## Generated Tests

The starter's own resource tests enforce:

- identical message and validator keys in the English and French catalogues;
- absence of the known hardcoded English strings being replaced;
- generated locale configuration, entity persistence, subscriber, controller,
  selector component, and mailer wiring;
- no additional custom Stimulus controller.

The application-owned functional suite verifies:

- French browser negotiation for a first-time visitor;
- English fallback for unsupported browser languages;
- cookie selection and persistence across requests;
- authenticated `User.locale` precedence over cookie and browser language;
- persistence of an authenticated language change;
- registration initialized from the resolved locale;
- CSRF rejection, unsupported-locale rejection, and safe redirect handling;
- representative French public, authentication, account, validation, and
  email subject/body output.

Both fresh skeleton and webapp smoke tests continue to remove `te4g/starter`
before running the generated application suite.

## Documentation

The README and customization guide explain the default resolution order,
English/French catalogues, the `User.locale` field, and how an application can
add another supported locale without editing vendor code.

## Out of Scope

- Locale-prefixed URLs such as `/fr/login`.
- Automatic machine translation.
- JavaScript-only locale selection.
- Translating application-specific content created after generation.
- Adding languages other than English and French in this change.
